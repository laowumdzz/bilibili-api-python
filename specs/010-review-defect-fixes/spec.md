# Feature Specification: 评审缺陷修复

**Feature Branch**: `010-review-defect-fixes`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "制定当前评审发现的修复计划：修复扫码登录轮询 dict 参数 TypeError、Api(headers=) 清空请求头、data 布尔值错位写入 params、异常子模块路径兼容、registry 类别映射缺失等缺陷"

**背景**: 2026-10-23 对当前 HEAD（`2e2fd63`）与首次提交（`99648df`）的全量代码评审发现五项已复现或可推演的缺陷，本特性将其作为一次收口修复：

1. **扫码登录轮询不可用（高优先级，已复现）**：网页扫码登录轮询请求的两个结构化查询参数（`x-bili-locale-json`、`x-bili-device-req-json`）以对象字面量形式传入，默认 `aiohttp` 客户端在参数编码阶段直接抛 `TypeError`，请求不会发出（本地回环复现：服务端收到 0 个请求）。该缺陷由两个历史提交交互产生——`623d71b` 加入这些参数时默认客户端还是 CurlCFFI，移除 CurlCFFI 的提交（`b3d03ec`）使 `aiohttp` 成为默认后暴露。既有离线用例在 `Api` 层打桩，未覆盖客户端编码边界，因此门禁全绿但真实链路不可用；`scripts/login_and_cache.py qrcode` 与 `pytest --login qrcode` 均受影响。
2. **显式请求头被清空（中优先级，已复现）**：`Api` 构造阶段会把显式传入的自定义请求头的值全部置为空串（设计上要求随后经 `update_headers` 恢复），而唯一在构造参数中直接传 `headers=` 的调用点（短信风控二次验证的交换分支）没有恢复步骤，实际发送 `User-Agent: ""` / `Referer: ""`。该行为自首次提交即存在，重构未修。
3. **请求体布尔值错位（中优先级，已复现）**：请求准备阶段把 `data` 中的布尔值写入查询参数（`new_params`）而非请求体（`new_data`），属首次提交即存在的一行笔误。当前库内没有以布尔字面量调用 `update_data` 的点（AST 扫描确认），但这是公开调用链上的潜伏缺陷，下游以布尔字段调用时字段会从请求体迁移到查询参数。
4. **异常子模块导入路径断裂（中优先级，已验证）**：重构将 17 个按类拆分的异常模块并入 `exceptions/_simple.py`，包级导出（`from bilibili_api.exceptions import ...`）与 `__all__` 不变，但子模块路径（如 `bilibili_api.exceptions.ArgsException`）现在以 `ModuleNotFoundError` 失败。项目自身测试仍以子模块路径导入 `ResponseCodeException`，说明该写法在生态中真实存在；且该兼容性破坏未在变更记录中告知。
5. **registry 类别映射缺失（中优先级，可推演）**：同步脚本的类别映射表缺 `broadcast` / `cheese` / `opus` 三个类别。当前这三个类别的全部条目因 URL 已存在而在解析前被跳过（dry-run 输出 609 条全部已存在、新增 0），所以暂不报错；一旦这些类别出现新接口，映射查表将直接 `KeyError`。

评审同时发现三项低优先级加固项（上传文件句柄未显式关闭、`Credential` 字符串化未脱敏、文档漂移校验的 mypy 缓存过期提示），**不在本特性范围内**，留待独立特性处理。

## Clarifications

- Q: 扫码登录轮询这类"值为字典"的查询参数，应该在请求准备的统一层自动做 JSON 序列化，还是只在调用点或客户端层局部处理？ → A: 统一请求准备层——构造请求时把任何值为字典的查询参数自动转为紧凑 JSON 字符串，对全部调用点生效（选项 A）。
- Q: 扫码轮询里那两个浏览器复刻参数（`x-bili-locale-json`、`x-bili-device-req-json`）在修好编码之后是保留还是直接删掉？ → A: 保留两个参数，编码修正后照常发送，维持浏览器行为复刻（选项 A；真机验证后如证明服务端不要求，可另行裁决删除）。
- Q: 被移除的 17 个按类异常子模块导入路径，应该恢复成薄兼容模块，还是不恢复、只在变更记录中告知破坏？ → A: 恢复全部 17 个子模块薄兼容层（仅 re-export，类对象与包级导出同一），并在变更记录留痕（选项 A）。
- Q: registry 里缺映射的三个类别（`broadcast` / `cheese` / `opus`）应该补进映射表真正可同步，还是只加"未知类别跳过并告警"的兜底？ → A: 补齐三类别映射（`cheese` / `opus` 落既有定义文件，`broadcast` 无既有文件时经同步新建），同时保留对映射表未覆盖类别的"跳过 + 告警"兜底（选项 A）。
- Q: 宪法 IV 字面"禁止网络请求"与扫码轮回环测试设计（本地 `127.0.0.1` 服务器驱动真实客户端栈）冲突如何裁决？ → A: 按宪章 Governance 程序出 v1.2.1 PATCH 修订，明确离线边界为"不触外网"，本机回环测试服务器属本机进程间通信、允许（分析轮 C1，方案 a）。
- Q: SC-004"预览输出逐字一致"与汇总行新增"无映射跳过"计数项冲突如何裁决？ → A: 修订 SC-004 与 US5 场景 4 为计数语义一致（已存在 609 / 新增 0 / 无映射跳过 0），汇总行扩展属设计内变更（分析轮 I1，方案 a）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 扫码登录用户在默认客户端下完成网页扫码登录 (Priority: P1)

一个下游用户在默认客户端（`aiohttp`）环境下使用网页扫码登录：生成二维码、扫码、轮询状态、登录成功后取得凭据，全流程正常工作。轮询请求能够真正发出并被服务端接受，两个结构化参数以服务端可解析的紧凑 JSON 字符串编码；轮询状态映射（待扫码 / 已扫码待确认 / 过期 / 成功）与凭据构造（Set-Cookie 采集、必需字段校验、`ac_time_value` 可选）保持既有契约不变。

**Why this priority**: 这是主登录链路的完全性故障——请求根本发不出去，`login_and_cache.py qrcode` 与 `pytest --login qrcode` 均不可用；且既有离线测试因打桩位置过高而全绿，属于最需要优先修复并补测试盲区的缺陷。

**Independent Test**: 离线——在客户端编码边界（而非 `Api` 方法层）断言轮询请求的实际查询参数：全部为标量，且两个结构化参数为合法 JSON 字符串（UTF-8 内容、紧凑分隔符），修复前该用例应失败；真机——扫码全流程（生成 → 轮询 → `get_credential()`）验收成功。

**Acceptance Scenarios**:

1. **Given** 已生成二维码且用户已扫码，**When** 轮询登录状态，**Then** 请求经默认客户端成功发出，不再因参数类型在编码阶段抛错，轮询返回的状态被正确映射为四种登录事件之一。
2. **Given** 轮询成功且响应下发必需 Cookie，**When** 构造凭据，**Then** 行为与特性 002 / 006 的既有契约一致（SESSDATA / bili_jct / DedeUserID 必需，`ac_time_value` 可选）。
3. **Given** 任一查询参数的值为结构化对象，**When** 请求准备完成，**Then** 其被序列化为合法 JSON 字符串，不出现 Python 字典 repr 形态（单引号、非紧凑）。

### User Story 2 - 二次风控验证用户请求携带正确的浏览器标识 (Priority: P2)

一个触发短信二次风控验证的用户（密码 / 短信登录后进入 `LoginCheck` 分支），其交换请求携带库声明的 User-Agent 与 Referer 正常完成验证；任何调用方显式传入的自定义请求头都能原样送达，不再被静默清空为空串。

**Why this priority**: 影响登录链路的一个分支（非主路径），缺陷自上游继承且长期未被发现，修复成本低、收益明确；优先级低于扫码主链路。

**Independent Test**: 离线——构造携带自定义请求头的请求，在请求准备边界断言每个头的名称与值原样保留；对与既有交换调用点同形的构造场景（同一接口定义 + `headers=` + `no_csrf=True`）在同一边界断言请求头非空。

**Acceptance Scenarios**:

1. **Given** 调用方在构造请求时显式传入自定义请求头，**When** 请求发出，**Then** 每个头的名称与值原样送达（值仅在调用方本人传空串时为空串）。
2. **Given** 短信风控交换分支执行，**When** 交换请求发出，**Then** 携带其声明的 User-Agent 与 Referer，不再是空值。

### User Story 3 - 调用方以布尔值作为请求体字段时取值位置正确 (Priority: P2)

一个下游调用方在请求体中以布尔字段调用接口（如开关类参数），字段以 0/1 形式保留在请求体中发送；查询参数不受影响，值为 `None` 的字段剔除行为与现状一致。

**Why this priority**: 当前库内无触发点，属公开调用链上的潜伏缺陷，用户面为潜在受影响而非已发生故障；但修复是一行改动加回归测试，成本低，随本特性一并收口。

**Independent Test**: 离线——以布尔与普通字段混合构造请求，断言准备结果中请求体含 0/1 化的布尔字段、查询参数不含该键、`None` 字段仍被剔除、查询参数中的布尔转整数行为不变。

**Acceptance Scenarios**:

1. **Given** 请求体同时含布尔字段与普通字段，**When** 请求准备，**Then** 布尔字段以 0/1 出现在请求体，查询参数中不含该键。
2. **Given** 请求体含 `None` 值字段，**When** 请求准备，**Then** 该字段被剔除（现状不变），其余字段不受影响。

---

### User Story 4 - 下游按子模块路径导入异常类不再断裂 (Priority: P2)

一个此前按"子模块路径"导入异常类的下游用户（如 `from bilibili_api.exceptions.ArgsException import ArgsException`，历史上全部 22 个按类模块路径均存在）在升级后导入照常成功，得到的异常类与包级导出是同一对象，`except` 捕获行为不变；使用包级导入的用户完全无感。该兼容性恢复同时在变更记录中留痕。

**Why this priority**: 属于已发生但未告知的兼容性破坏，影响面取决于下游导入习惯（项目自身测试即存在该写法）；不阻断运行时主链路，故排在两个运行时故事之后，但作为契约修复必须随本特性完成。

**Independent Test**: 离线——对首次提交存在过的全部按类异常模块路径逐一导入并断言：导入成功、类对象与包级导出相同、包级 `__all__` 集合不变。

**Acceptance Scenarios**:

1. **Given** 下游代码使用历史上任一按类异常子模块路径导入，**When** 导入，**Then** 成功且得到的类与包级导出为同一对象（`is` 判定为真）。
2. **Given** 下游代码使用包级导入，**When** 导入，**Then** 可导入集合与行为与修复前完全一致。
3. **Given** 下游查阅变更记录，**When** 了解本次兼容性恢复，**Then** 记录明确说明恢复了哪些导入路径及其原因。

---

### User Story 5 - 维护者同步 registry 时未知类别不再崩溃 (Priority: P3)

维护者运行 registry 同步（含预览模式）时，任意类别的条目要么被正确映射落位、要么被显式跳过并输出含类别名与条目数的告警，进程不因映射表缺项而崩溃；纯增量契约（已存在条目一律不动、gRPC 与 `method=OTHER` 条目跳过）与当前全量同步结果（609 条全部已存在、新增 0）保持不变。

**Why this priority**: 当前为休眠缺陷（相关类别条目均已存在），只在 registry 未来新增接口时触发；但它是流程健壮性问题且修复局部、可离线验证，随本特性一并收口。

**Independent Test**: 离线——对类别映射解析逻辑做单元验证：已映射类别（含 `broadcast` / `cheese` / `opus`）正确解析目标，未映射的虚构类别被跳过并告警；对本机当前全量 registry 的预览计数与修复前语义一致。

**Acceptance Scenarios**:

1. **Given** registry 中 `broadcast` / `cheese` / `opus` 类别出现待同步条目，**When** 运行同步或预览，**Then** 条目按补齐后的映射落位同步（`cheese` / `opus` 进入既有定义文件，`broadcast` 无既有文件时新建），进程不崩溃。
2. **Given** registry 中某映射表仍未覆盖的新类别出现待同步条目，**When** 运行同步或预览，**Then** 条目被显式跳过并输出含类别名与条目数的告警，进程不因映射缺失崩溃。
3. **Given** 条目 URL 已存在于接口定义，**When** 同步，**Then** 该条目依旧跳过不动（纯增量契约不变）。
4. **Given** 本机当前全量 registry，**When** 预览运行，**Then** 同步结果与修复前一致（609 条全部已存在、新增 0、无映射跳过 0、无未映射告警），即修复本身不改变现有同步结果；汇总行新增"无映射跳过"计数项属设计内变更，不要求逐字相同。

### Edge Cases

- 结构化参数序列化口径：JSON 编码需与服务端兼容（紧凑分隔符、非 ASCII 内容以 UTF-8 保留），与浏览器实际行为对齐；序列化失败（理论不可达）按普通参数错误处理，不静默吞掉。
- 服务端对 `x-bili-*` 参数不识别或忽略时，轮询仍应成功——当前接口定义仅声明 `qrcode_key` 与 `source`，这两个参数是浏览器行为复刻，修复只改编码形态，不改变其存在性。
- 异常兼容层的类对象必须与包级导出严格同一，避免 `except` 精确捕获失效；不得借机改变任何异常类的继承关系或构造签名。
- 布尔修复不得影响既有"查询参数中布尔转整数"与"`None` 剔除"行为，也不得影响 JSON 请求体场景。
- 同步脚本的"已存在跳过"与"无映射跳过"两类输出必须可区分，避免维护者误判同步结果。
- 全部新增回归用例必须离线可跑（不触网、不用真实凭据、不改账号状态）；需要真机的验收项走既有 cred 分层与登录脚本。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 网页扫码登录轮询请求 MUST 在默认客户端下成功发出，不得因查询参数值类型在客户端编码阶段抛错。
- **FR-002**: 请求准备的统一层 MUST 把任何"值为字典"的查询参数自动序列化为合法 JSON 字符串（紧凑分隔符、内容以 UTF-8 保留），MUST NOT 以 Python 字典 repr 形态发送，该行为对全部调用点生效（当前已知触发点为扫码轮询的两个结构化参数）；轮询的状态映射、Set-Cookie 采集与凭据构造行为 MUST 保持特性 002 / 006 的既有契约不变。
- **FR-003**: 通过构造参数显式传入的自定义请求头 MUST 原样送达（名称与值不被清空）；短信风控交换请求 MUST 携带其声明的 User-Agent 与 Referer。
- **FR-004**: 请求体中的布尔值 MUST 转为整数后保留在请求体，MUST NOT 出现在查询参数；查询参数中的布尔转整数与字段 `None` 剔除行为 MUST 保持不变。
- **FR-005**: 首次提交存在过的全部按类异常子模块导入路径 MUST 恢复可用（导入成功且与包级导出为同一类对象）；包级导入面与 `__all__` MUST 保持不变；该兼容性恢复 MUST 在变更记录中留痕。
- **FR-006**: registry 同步 MUST 对任意类别稳健：`broadcast` / `cheese` / `opus` 三个类别 MUST 补入类别映射（`cheese` / `opus` 落既有定义文件，`broadcast` 无既有文件时经同步新建）；映射表未覆盖的类别 MUST 显式跳过并输出含类别名与条目数的告警，MUST NOT 因映射缺失崩溃；纯增量契约（已存在条目不动、gRPC 与 `method=OTHER` 跳过、registry 元数据不进入接口定义）MUST 保持。
- **FR-007**: 每项修复 MUST 附离线回归测试（不触网、不用真实凭据、不改账号状态），且断言位置必须覆盖此前测试盲区：扫码轮询用例 MUST 在客户端编码边界断言实际外发查询参数，请求头与请求体用例 MUST 在请求准备边界断言实际外发内容。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 网页扫码登录全流程（生成二维码 → 轮询 → 获取凭据）在默认客户端下真机验收成功；对应的离线回归用例无需凭据即可区分修复前后行为（修复前失败、修复后通过）。
- **SC-002**: 本特性新增的全部离线回归用例通过，且项目全量质量门禁（静态检查、类型检查、文档一致性校验、离线测试）零失败。
- **SC-003**: 首次提交存在过的全部按类异常子模块导入路径（22 个历史路径）经离线用例逐一验证可用，包级导出集合与修复前完全一致。
- **SC-004**: 在包含未映射类别待同步条目的数据集上运行同步预览不崩溃并产生含类别名与条目数的告警；对本机当前全量 registry 的预览计数语义与修复前一致（已存在 609、新增 0、无映射跳过 0、无未映射告警、不产生新文件），汇总行因新增"无映射跳过"计数项而扩展属设计内变更，不要求逐字相同。

## Assumptions

- 五项缺陷全部纳入本特性范围；评审发现的三项低优先级加固项（上传文件句柄显式关闭、`Credential` 字符串化脱敏、文档漂移校验的缓存重建流程）不在范围内，留待独立特性。
- `x-bili-locale-json` / `x-bili-device-req-json` 两个参数默认保留（不删除），仅修正编码形态；若真机验证表明服务端不要求这些参数，可另行裁决删除，但本特性默认按"保留 + 正确序列化"执行。
