# Feature Specification: 集成测试按重要程度分级重构（凭证账号保护）

**Feature Branch**: `007-credential-test-tiers`

**Created**: 2026-09-26

**Status**: Draft

**Input**: User description: "因为测试时的凭证账号有限，并且受风控影响，请你按重要程度重新设计 pytest 需要凭证的测试，当前可用的凭证账号位于 TEMP 目录 bilibili_api_pytest_login.json（base64 编码）。测试时确保重要的凭证测试项能全部通过。"

**背景**: 当前集成测试套件共 313 个用例（38 个文件），其中约 200 个需要登录凭据，但全部平铺在 `integration` 一个层级里，而实际可用的测试凭据只有**一个共享账号**（TEMP 缓存文件自动装配）。平铺执行的问题：请求总量巨大且默认无限速（`BILI_RATELIMIT` 缺省 0），极易触发 412 风控；用例中夹杂真金消费（直播间金瓜子送礼）、对第三方高流量视频的公开评论、破坏性操作（清空账号整个稍后再看列表）、仅特定账号身份可用的操作（房管封禁、创作中心）等高危行为；多个文件依赖跨用例全局变量传递资源 ID（评论 ID、收藏夹 ID、观影房间等），子集运行必然失败。结果是"想只跑重要的测试"既没有选择手段，也没有安全边界。

**目标**: 把需要凭据的集成用例按重要程度划分为四个层级（核心冒烟 → 核心读回归 → 可自清理写生命周期 → 高危显式门控），配套选择命令、安全默认限速与顺序无关化改造，使维护者在单账号条件下，一条命令即可稳定跑通全部"重要"用例且不伤害账号。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一条命令跑通核心冒烟层 (Priority: P1)

库维护者在对集成链路最有信心的最小集合上做快速验证：用单一命令选择**核心冒烟层**（最高重要级），覆盖反爬参数链路（buvid 生成、bili_ticket 获取、Wbi 签名）、自身信息读取、视频与用户核心信息读取等最关键路径。该层全部只读、请求总量有显式上限、对账号无任何状态影响，在共享单账号上每次运行都应当通过。

**Why this priority**: 这是"重要凭证测试项能全部通过"的底线集合——登录态可用、反爬签名有效、核心读接口通，三者构成库可用性的最小说明。若该层不绿，其余一切分层失去意义。

**Independent Test**: 以 TEMP 缓存的可用凭据运行核心冒烟层选择命令，断言全部用例通过、零写操作、总请求数不超过层内预算。

**Acceptance Scenarios**:

1. **Given** TEMP 缓存存在有效凭据，**When** 运行核心冒烟层选择命令，**Then** 该层全部用例通过（无失败、无错误）。
2. **Given** 核心冒烟层任意用例，**When** 检查其请求，**Then** 均为只读请求，不改变账号任何状态。
3. **Given** 核心冒烟层整层运行，**When** 统计对外请求数，**Then** 不超过该层定义的请求预算上限。
4. **Given** 某接口上游已死或长期风控（容错码用例），**When** 分级归层，**Then** 该用例不进入核心冒烟层。

---

### User Story 2 - 核心读回归层全绿 (Priority: P2)

维护者需要更完整的读路径回归：在核心冒烟层之上叠加**核心读回归层**，覆盖视频、用户、评论读、动态读、直播读、收藏夹读、搜索全量、番剧、排行榜等核心模块的主要只读接口。该层同样全部只读，但请求量更大，运行时自动启用用例间安全间隔，确保单账号下不触发 412 且全部通过。

**Why this priority**: 读接口占库接口绝大多数，是回归覆盖的主体；在"重要"定义中仅次于冒烟底线。只读属性保证它对账号零伤害，是继冒烟层之后最值得保障全绿的一层。

**Independent Test**: 以 TEMP 缓存凭据运行"冒烟层 + 读回归层"累加范围选择命令，断言全部通过、无 412 风控错误、总时长在预算内。

**Acceptance Scenarios**:

1. **Given** 有效凭据，**When** 运行冒烟层 + 读回归层的累加选择命令，**Then** 全部用例通过，全程无 412 错误。
2. **Given** 该层包含的循环遍历型用例（如全分区榜单遍历、批量链接解析、互动视频图遍历），**When** 执行，**Then** 循环内部有节流或遍历规模被缩减到预算内，不会连发大量请求。
3. **Given** 读回归层运行，**When** 结束，**Then** 账号状态与运行前一致（无任何写操作副作用）。

---

### User Story 3 - 写操作生命周期层自清理 (Priority: P3)

维护者需要验证库的写能力（点赞、收藏、关注、评论发送、弹幕发送、稍后再看增删等），但写操作消耗账号状态且暴露于风控。**写生命周期层**中的每个用例都必须自包含"执行写 → 验证生效 → 恢复原状"的闭环：完整跑完该层后，账号的关注列表、收藏、点赞、评论、弹幕、稍后再看与运行前完全一致。

**Why this priority**: 写路径是库的核心能力之一，必须有回归保障；但其账号成本决定了它排在两层只读之下，且必须以"可完全恢复"为前提才能纳入常规验证。

**Independent Test**: 以 TEMP 缓存凭据运行"冒烟 + 读回归 + 写生命周期"累加范围选择命令，断言全部通过；运行前后对比账号状态（关注 / 收藏 / 点赞 / 评论 / 弹幕 / 稍后再看）无残留差异。

**Acceptance Scenarios**:

1. **Given** 有效凭据，**When** 运行包含写生命周期层的累加命令，**Then** 全部用例通过，且每个写用例的恢复步骤断言成功（如点赞后取消点赞、评论发送后删除、关注后取关）。
2. **Given** 写生命周期层的评论类用例，**When** 执行，**Then** 评论发布目标为账号自有内容，不在任何第三方内容上公开发布测试评论。
3. **Given** 写用例的清理步骤失败，**When** 用例收尾，**Then** 报告明确的残留警告而非静默吞掉，且不掩盖原始失败原因。
4. **Given** 完整跑完写生命周期层，**When** 事后核对账号，**Then** 无任何运行残留（关注 / 收藏 / 点赞 / 评论 / 弹幕 / 稍后再看均恢复）。

---

### User Story 4 - 高危操作显式门控、默认永不执行 (Priority: P4)

真金消费（金瓜子送礼）、付费投币 / 三连、清空稍后再看等破坏性操作、私信发送、创作中心全量接口、房管操作等高危用例，在单共享账号条件下不可安全执行。它们被归入**高危显式门控层**：任何默认运行与累加范围选择都不会执行它们，只有显式点名该层（或该层内用例）时才运行——为将来拥有牺牲账号的环境保留覆盖。

**Why this priority**: 该层不参与"重要用例全绿"的目标，其价值在于把危险操作从常规路径中物理隔离。隔离本身优先级低于三层常规验证，但不可缺省——否则单账号一次误运行就可能造成真实资金损失或不可逆账号状态变更。

**Independent Test**: 运行默认全量命令与各累加范围命令，断言高危层用例零执行（收集即被排除）；再显式点名高危层，断言仅在该模式下执行。

**Acceptance Scenarios**:

1. **Given** 有效凭据，**When** 不带任何层级选择运行默认命令，**Then** 高危门控层用例一个都不执行。
2. **Given** 有效凭据，**When** 运行任何累加范围选择（冒烟、冒烟 + 读回归、冒烟 + 读回归 + 写生命周期），**Then** 高危门控层用例同样零执行。
3. **Given** 维护者显式点名高危层，**When** 运行，**Then** 仅该层用例执行（此模式不在本特性验收范围，仅保留能力）。
4. **Given** 清空稍后再看类破坏性用例，**When** 分级归层，**Then** 必须位于高危门控层，绝不进入任何默认执行的层级。

---

### User Story 5 - 用例顺序无关、任意子集可独立运行 (Priority: P5)

分级运行天然是子集运行：维护者会按层选择、按文件选择、甚至单个用例点名运行。当前跨用例全局变量传递资源 ID（评论 ID、收藏夹 ID、观影房间、投票 ID 等）的模式使任何子集运行必挂。本特性要求所有凭据用例顺序无关：资源在用例或夹具内创建与销毁，任意单个用例独立运行均可通过。

**Why this priority**: 它是前四个故事成立的结构性前提——层级选择命令产生的正是子集，顺序依赖会让"重要用例全绿"在子集形态下直接失效。

**Independent Test**: 从三个常规层各抽取若干用例（含原全局变量依赖型，如评论生命周期、收藏夹生命周期），以单用例方式独立运行，断言全部通过。

**Acceptance Scenarios**:

1. **Given** 原依赖全局变量的评论生命周期用例组，**When** 仅运行其中"回复 / 点赞 / 删除"任一单个用例，**Then** 所需评论资源由该用例（或其夹具）自行创建，用例通过。
2. **Given** 原依赖全局变量的收藏夹生命周期用例组，**When** 仅运行"修改 / 复制 / 移动 / 删除"任一单个用例，**Then** 所需收藏夹资源自建自清，用例通过。
3. **Given** 三个常规层中的任意用例，**When** 以 `-k` 或文件名单独运行，**Then** 不因缺少其他用例的副作用而失败。

---

### User Story 6 - 凭据用例默认安全限速 (Priority: P6)

维护者在本地直接运行命令（未设置任何环境变量）时，凭据用例之间默认启用非零安全间隔；循环遍历型用例在循环体内节流。当前默认间隔为 0，是触发 412 的直接原因之一。安全默认值可经环境变量覆盖（含调大调小），但缺省必须安全。

**Why this priority**: 限速是"重要用例全部通过"的保障条件而非独立能力，排最后；但没有它，前几层在单账号上的全绿目标随时可能被风控打断。

**Independent Test**: 不设任何环境变量运行冒烟 + 读回归层，断言相邻凭据用例之间存在默认间隔、全程无 412；设置覆盖变量后间隔按覆盖值生效。

**Acceptance Scenarios**:

1. **Given** 未设置限速环境变量的本地环境，**When** 运行凭据用例，**Then** 相邻用例间存在非零默认间隔。
2. **Given** 维护者通过环境变量显式设定间隔，**When** 运行，**Then** 实际间隔以覆盖值为准（既有变量语义保留）。
3. **Given** 循环遍历型用例（全分区榜单、批量链接解析、互动视频图遍历），**When** 执行，**Then** 循环体内有节流，单用例不再连发数十个无间隔请求。

---

### Edge Cases

- 凭据缺失或全部来源不可用时如何处理？——全部分级用例自动跳过，跳过过程零网络请求；离线用例不受任何影响（沿用现状语义）。
- 凭据在运行中途过期如何处理？——沿用现状失败语义（接口报错即用例失败），不引入运行中自动重登；维护者可用既有 `--login` 重新登录后重跑。
- 上游接口已死（-404）或长期风控（-352）的用例如何归层？——保留既有容错码断言，但一律不进入核心冒烟层；可在读回归层保留。
- 账号状态差异（无硬币、非 VIP、非房管、无粉丝牌）导致写用例被服务端拒绝如何处理？——沿用既有容忍码机制（如 -104 无硬币、非管理员码），容忍即视为通过；核心冒烟层不依赖任何账号身份特权。
- 清理步骤因风控或接口抖动失败如何处理？——重试有限次数后报告残留警告，不掩盖原始失败，不让清理失败伪装成用例通过。
- 一次运行中同一写目标被多个用例先后操作（如同一视频先点赞后收藏）如何处理？——允许，但每个用例只恢复自己执行的操作，互不假设对方的中间状态。
- 匿名集成用例（不需要凭据的集成用例，如热门、排行、番剧读）如何处理？——不强制归层，保持现有 `integration` 标记照常运行；仅"需要凭据的用例"强制分级。
- 现有 `readonly` PR 门禁子集与核心冒烟层的关系如何处理？——`pytest -m readonly` 命令语义保持不变照常工作；核心冒烟层是其超集，两者标记并存不冲突。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个需要凭据的集成用例 MUST 恰好归属四个重要级之一（下称 cred0 / cred1 / cred2 / cred3），以用例上显式可审计的标记声明；存在未标注的需凭据用例时，测试套件自身 MUST 给出可发现的告警或阻断，防止漏标。
- **FR-002**: 分级判据 MUST 成文并统一适用：cred0 = 只读、接口稳定（稳定 = 不依赖 FR-012 所列容错码）、请求量小（核心冒烟）；cred1 = 核心模块主读路径回归（只读）；cred2 = 可完全恢复的写操作生命周期；cred3 = 真金消费、破坏性操作、高风控暴露或需特定账号身份的操作。
- **FR-003**: 测试运行器 MUST 支持按单层与累加范围选择（cred0；cred0+cred1；cred0+cred1+cred2），且默认全量运行的执行范围 MUST 等同 cred0–cred2；cred3 MUST 仅在显式点名该层或其中用例时执行。
- **FR-004**: cred0 在可用凭据条件下 MUST 100% 通过：全部只读、零账号状态影响、整层对外请求数不超过 30 次（以运行时统计可核验；请求计数口径以层级选择器契约为准——服务端视角全计数）。
- **FR-005**: cred0+cred1 累加运行在可用凭据条件下 MUST 100% 通过且全程零 412 风控错误——判定口径为全统计零容忍：412 及等效风控错误码（如 -352）均计入，偶发亦不豁免；验收运行中任一 412 类错误实际发生时 MUST 立即中止运行以防加重，该次运行判为验收失败。两层合计对外请求数不超过 400 次（计数口径同 FR-004）；上游已死接口的容错码断言通过视为通过。
- **FR-006**: cred2 的每个写用例 MUST 自带配对恢复（执行写 → 验证生效 → 恢复原状），恢复结果 MUST 有断言或明确的残留警告；生命周期用例的清理 MUST 以 teardown 级义务执行——无论用例成功、失败、超时或中断，清理步骤 MUST 照常运行；cred0–cred2 完整运行后账号状态（关注 / 收藏 / 点赞 / 评论 / 弹幕 / 稍后再看）MUST 与运行前一致。
- **FR-007**: 真金消费（金瓜子送礼）、破坏性操作（清空稍后再看、删除观看记录等）、私信发送、创作中心全量接口、房管操作 MUST 归入 cred3；其中破坏性操作 MUST NOT 出现在 cred0–cred2 任何一层。
- **FR-008**: cred2 的公开发布类写操作（评论等）MUST 以账号自有内容为对象；MUST NOT 在任何第三方内容上公开发布测试评论（现行对热门视频 av271 的公开评论用例 MUST 改道）。
- **FR-009**: 全部凭据用例 MUST 顺序无关：MUST NOT 依赖跨用例全局变量传递资源标识；所需资源 MUST 在用例或其夹具内创建并在结束时清理；任意子集（含单用例）独立运行 MUST 通过。
- **FR-010**: 凭据用例之间 MUST 启用非零的默认安全间隔（现有环境变量覆盖语义保留）；循环遍历型用例 MUST 在循环内节流或将遍历规模缩减至请求预算内（请求预算仅定义于 cred0 / cred1，见 FR-004 / FR-005；本项约束 cred0 / cred1 层循环，cred3 不默认执行、无预算义务）。
- **FR-011**: 缺凭据时全部分级用例 MUST 自动跳过且跳过过程零网络请求；离线用例与匿名集成用例的行为 MUST 与重构前一致。
- **FR-012**: 容忍上游已死 / 风控降级接口的既有容错码语义 MUST 保留，此类用例 MUST NOT 归入 cred0。
- **FR-013**: 既有 `readonly` 标记与 `pytest -m readonly` 命令语义 MUST 保持可用（PR 门禁回路不变）。
- **FR-014**: 分级体系、各级判据、选择命令、账号安全策略与 cred3 显式执行方式 MUST 成文于项目测试文档（AGENTS.md 测试节或等效位置）。

### Key Entities

- **重要级（Tier）**: 凭据用例的安全与价值分级。属性：层级标识（cred0–cred3）、准入判据（读 / 写 / 可逆性 / 资源消耗 / 风控暴露）、请求预算、清理要求。与用例为一对多绑定。
- **凭据用例（Credential Test）**: 需要登录态的集成用例。属性：所属层级、读 / 写属性、配对恢复动作、请求量估计、容错码集合。
- **账号安全策略（Account Safety Policy）**: 单共享账号下允许默认执行 / 仅显式执行 / 禁止执行的操作清单及依据，是分级判据的权威来源。
- **层级选择器（Tier Selector）**: 维护者侧的运行入口约定：单层选择、累加范围选择、高危层显式点名三种形态，与默认全量运行的层级范围约定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 以 TEMP 缓存的单一可用账号运行 cred0 选择命令，通过率 100%（无失败、无错误；除缺凭据跳过外无跳过），整层对外请求数不超过 30 次。
- **SC-002**: 以同一账号运行 cred0+cred1 累加命令，通过率 100%，全程零 412 风控错误（判定与处置口径见 FR-005），两层合计对外请求数不超过 400 次（计数口径见 FR-004），总时长不超过 30 分钟；本项验收 MUST 在默认限速（不设 BILI_RATELIMIT 覆盖）与单一共享账号环境下执行，其他环境下的全绿结果不构成验收通过。
- **SC-003**: 以同一账号完整运行 cred0–cred2，通过率 100%；运行前后账号关注 / 收藏 / 点赞 / 评论 / 弹幕 / 稍后再看六项状态逐项比对无差异。
- **SC-004**: 不带层级选择运行默认全量命令，cred3 用例执行数为 0；显式点名 cred3 时仅执行该层（本项在验收中以"收集即排除"方式核验，不真机执行高危操作）。
- **SC-005**: 从 cred0 / cred1 / cred2 各层独立抽取用例（须覆盖原全局变量依赖的评论与收藏夹生命周期组）单用例运行，通过率 100%。
- **SC-006**: 无凭据环境中全部分级用例自动跳过、跳过期间零网络请求，离线套件结果与重构前完全一致；`pytest -m readonly` 在 PR 门禁回路行为不变。
- **SC-007**: cred0+cred1 的总请求数以 FR-005 预算为准（≤400 次），较重构前"全部凭据用例平铺运行"的等价读覆盖请求量明显下降（预算化收敛，重构前仅凭据用例即约 200 个用例的请求量远超该预算）。

## Assumptions

- 可用测试凭据仅一个共享账号（TEMP 缓存 `bilibili_api_pytest_login.json` 自动装配），本特性不新增账号；因此 cred3 的真机执行不在验收范围，仅验证"默认不执行 + 显式可点名"。
- 本特性只重组既有用例（归层 / 门控 / 顺序无关化 / 限速 / 写目标改道），不新增功能模块的集成覆盖缺口；login_v2 集成、视频上传链路等已知缺口随本特性成文于 AGENTS.md 测试节的"已知集成覆盖缺口"条目作为持续追踪去向，不在本特性实现范围内。
- conftest.py 的凭据装配链路（--login > TEMP 缓存 > BILI_* 环境变量 > .bilibili.cookie）与 `--login` 交互流程保持不变。
- 上游接口可用性与当前一致；已死接口维持现有容错码，不借本特性修复业务模块。
- 既有 `BILI_RATELIMIT` 环境变量语义保留，本特性仅将其缺省值从 0 调整为安全默认（或引入等效的安全缺省机制）。
- 分层命名（cred0–cred3）为规格内约定名，实现阶段可统一为项目风格一致的标记名，但四层语义与选择行为 MUST 与本规格一致。
