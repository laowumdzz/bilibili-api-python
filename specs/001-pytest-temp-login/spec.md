# Feature Specification: pytest 临时登录凭据（--login）

**Feature Branch**: `001-pytest-temp-login`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "在使用 pytest 测试时加入一个可选的命令行参数 --login <type>，表示可以使用手机号或二维码临时登录获取凭证来执行测试。获取到的凭证以 base64 编码后的格式存储在系统环境变量的 TEMP 文件夹，在每次测试时尝试获取该文件。1. 获取失败时(FileNotFound)：输出一条提示并继续执行，自动跳过所有需要凭证的测试；2. 找到文件但是文件内容不对：删除凭证文件，输出一条错误并继续执行，跳过凭证测试；3. 找到文件且内容正确：先验证凭证是否有效或过期——3.1 凭证未过期且有效：测试全部用例；3.2 凭证过期：尝试刷新，刷新失败时抛出警告并删除文件，继续并跳过凭证测试"

## Clarifications

### Session 2026-08-31

- Q: 缓存凭据与既有凭据来源（`BILI_*` 环境变量、`.bilibili.cookie`）并存时，取用优先级如何排序？ → A: 缓存最高：本次 `--login` 强制登录 > TEMP 缓存 > `BILI_*` 环境变量 > `.bilibili.cookie`；无缓存时行为与现状完全一致（已确认）
- Q: 传入 `--login` 但缓存凭据仍有效时，强制重新登录还是复用缓存？ → A: 强制重新登录：只要显式传入 `--login` 就无条件执行所选登录流程并以新凭据覆盖缓存，"能复用则复用"的语义只属于不带 `--login` 的普通运行（已确认）
- Q: 二维码超过平台有效期仍未扫码确认时如何处理？ → A: 自动重新生成新二维码并提示重新扫码，连续 3 次超时后明确中止登录流程（不产生缓存文件）（已确认）

## 用户场景与测试 *(mandatory)*

### User Story 1 - 扫码临时登录执行全量测试 (Priority: P1)

开发者本机没有任何配置好的凭据（无环境变量、无 `.bilibili.cookie`），希望不手工导出 Cookie 就能跑通需要登录的集成用例。开发者执行 `pytest --login qrcode`，终端展示可扫描的登录二维码；开发者用手机 App 扫码并确认后，测试进程获得临时登录凭据，将其以 base64 编码写入系统 TEMP 目录下的固定名称缓存文件，随后以该凭据执行全部用例（离线用例照常执行）。

**为何是这个优先级**: 这是本特性最核心的价值主张——零配置、一次扫码即可解锁全部集成测试；二维码方式无需输入任何账号敏感信息，是临时登录的最安全形态。

**独立测试**: 可以单独实现并验证：在无凭据环境下执行 `pytest --login qrcode`，完成扫码后集成用例不再因缺凭据而跳过，且 TEMP 目录中出现 base64 编码的缓存文件。

**验收场景**:

1. **Given** 本机无任何凭据来源，**When** 开发者执行 `pytest --login qrcode` 并用手机扫码确认，**Then** 登录成功、集成用例以新凭据执行、TEMP 目录生成 base64 编码的缓存文件
2. **Given** 开发者执行 `pytest --login qrcode`，**When** 二维码已生成但开发者尚未扫码，**Then** 进程等待扫码且不产生缓存文件
3. **Given** 开发者执行 `pytest --login qrcode`，**When** 连续 3 次二维码超时均无人扫码、或开发者在登录完成前主动中断流程，**Then** 登录流程明确终止并输出清晰提示、不产生缓存文件、离线用例仍正常执行、需凭据用例跳过

---

### User Story 2 - 手机号短信验证码临时登录 (Priority: P2)

开发者更习惯手机号登录，执行 `pytest --login phone`，按提示输入国家码与手机号；系统发送短信验证码（如触发极验或风控二次验证，则引导开发者完成）；开发者输入收到的验证码后获得凭据，后续存储与使用流程与扫码方式完全一致。

**为何是这个优先级**: 与扫码互为备选登录通道，覆盖没有 App 扫码条件或偏好短信的用户；实现于扫码之后可复用同一套凭据缓存与降级机制。

**独立测试**: 可以单独实现并验证：执行 `pytest --login phone`，输入手机号与短信验证码后集成用例以新凭据执行，缓存文件生成方式与扫码一致。

**验收场景**:

1. **Given** 本机无任何凭据来源，**When** 开发者执行 `pytest --login phone` 并依次完成手机号输入、验证码接收与输入，**Then** 登录成功、集成用例以新凭据执行、TEMP 目录生成缓存文件
2. **Given** 短信登录触发了风控二次验证，**When** 开发者按提示完成二次验证，**Then** 登录流程继续而非失败

---

### User Story 3 - 后续运行自动复用缓存凭据 (Priority: P3)

开发者首次登录后再次执行测试（不带 `--login`），测试进程自动尝试读取 TEMP 中的缓存文件：文件内容合法时先验证凭据是否有效或过期——未过期且有效则直接以该凭据执行全部用例，全程无任何交互；已过期则尝试刷新，刷新成功后以新凭据继续执行并更新缓存文件。

**为何是这个优先级**: "临时登录一次、后续免登录"是缓存存在的意义；它把一次交互的成本摊销到多次测试运行上。

**独立测试**: 可以单独实现并验证：在缓存文件有效时执行 `pytest`（不带 `--login`），集成用例全部执行且全程无登录交互；人为使凭据过期后执行，观察到刷新行为。

**验收场景**:

1. **Given** TEMP 中存在内容合法且未过期的缓存凭据，**When** 开发者执行 `pytest`（不带 `--login`），**Then** 集成用例全部执行、无任何登录交互、缓存文件保持不变
2. **Given** TEMP 中存在内容合法但已过期的缓存凭据，**When** 开发者执行 `pytest`，**Then** 系统尝试刷新凭据，刷新成功后集成用例执行且缓存文件被更新为新凭据

---

### User Story 4 - 缓存异常时的安全降级 (Priority: P4)

缓存文件缺失、内容损坏或凭据过期且刷新失败时，测试进程不崩溃、不阻断离线用例，按场景给出恰当反馈并跳过所有需要凭据的测试：缺失时输出一条提示；损坏时删除文件并输出一条错误；过期且刷新失败时发出警告并删除文件。

**为何是这个优先级**: 降级路径保证特性"永不把测试运行搞挂"，是可用性底线；排最后是因为它只在异常场景生效。

**独立测试**: 可以单独实现并验证：分别构造缺失、损坏、过期且不可刷新三种缓存状态，执行测试并核对提示信息、文件去留与用例跳过情况。

**验收场景**:

1. **Given** TEMP 中不存在缓存文件，**When** 开发者执行 `pytest`，**Then** 输出一条提示（说明缓存凭据文件不存在）、测试继续执行、需凭据用例自动跳过
2. **Given** TEMP 中的缓存文件内容不合法（无法按约定格式解码出完整凭据字段），**When** 开发者执行 `pytest`，**Then** 该文件被删除、输出一条错误、需凭据用例跳过、离线用例继续执行
3. **Given** 缓存凭据已过期且刷新失败，**When** 开发者执行 `pytest`，**Then** 发出一条警告、缓存文件被删除、需凭据用例跳过、测试进程正常结束

### 边界情况

- `--login` 传入不支持的 `<type>` 值（既非 `phone` 也非 `qrcode`）时如何处理？→ 视为用法错误，以明确的参数错误信息退出，不进入测试收集
- 二维码超过平台有效期仍未扫码 → 自动重新生成新二维码并提示重新扫码；连续 3 次超时仍未扫码则明确中止，且不得留下缓存文件
- 短信验证码输错或超时 → 给出重试或明确失败提示；失败时不产生缓存文件
- 登录交互被用户中断（如 Ctrl+C）→ 视为登录放弃：提示后继续执行离线用例，不产生缓存文件
- 缓存文件可以解码但缺少必需凭据字段 → 归入"内容不对"路径：删除文件、报错、跳过
- 凭据有效性验证请求自身因网络问题失败（无法区分有效/过期）→ 按无法确认处理：提示并跳过需凭据用例，但**不删除**缓存文件（文件本身未必有错）
- 系统 TEMP 目录不可写 → 登录仍可完成但当次给出明确错误提示，测试凭据仅当次有效
- 缓存有效性与既有凭据来源并存（环境变量 / `.bilibili.cookie` 同时存在）→ 按假定优先级取用，不产生双重登录或互相覆盖
- 刷新所需的配套材料（如刷新令牌）不在缓存中 → 视为刷新失败路径处理
- 多次临时登录同一台机器 → 固定文件名被最新一次登录覆盖，符合"临时"语义

## 需求 *(mandatory)*

### 功能需求

- **FR-001**: 测试命令 MUST 接受可选命令行参数 `--login <type>`，合法取值为 `phone`（手机号短信验证码）与 `qrcode`（二维码扫码）；传入该参数时 MUST 无条件执行所选登录流程——即使 TEMP 缓存中存在有效凭据也不得跳过登录，登录成功后以新凭据覆盖缓存；不传该参数时行为 MUST 与引入本特性之前完全一致
- **FR-002**: `--login` 传入非法 `<type>` 值时，系统 MUST 以明确的用法错误退出，且不执行任何登录或测试
- **FR-003**: `--login qrcode` 时系统 MUST 向用户展示可扫描的登录二维码，等待扫码确认后取得凭据；二维码超过平台有效期仍未完成扫码时 MUST 自动重新生成新二维码并提示重新扫码，连续 3 次超时后 MUST 明确中止登录流程（不写入缓存文件）
- **FR-004**: `--login phone` 时系统 MUST 交互式收集手机号（含国家码）与短信验证码（含平台要求的验证码补充流程），完成后取得凭据
- **FR-005**: 任一方式登录成功后，系统 MUST 将凭据以 base64 编码格式写入系统 TEMP 目录（由系统临时目录环境变量指定）下一个**固定名称**的缓存文件
- **FR-006**: 每次测试运行（无论是否带 `--login`）MUST 尝试读取该缓存文件作为凭据来源之一，取用优先级见 Assumptions
- **FR-007**: 缓存文件不存在（FileNotFound）时，系统 MUST 输出一条提示并继续执行；若最终无任何可用凭据来源，需凭据的测试 MUST 自动跳过
- **FR-008**: 缓存文件存在但内容不合法（base64 解码失败或解码后凭据字段不完整）时，系统 MUST 删除该文件、输出一条错误并继续执行，需凭据的测试跳过
- **FR-009**: 缓存文件内容合法时，系统 MUST 先验证凭据是否有效或过期，再决定后续行为
- **FR-010**: 凭据未过期且有效时，系统 MUST 使用该凭据执行全部用例（含需凭据的集成用例）
- **FR-011**: 凭据已过期时，系统 MUST 尝试刷新凭据；刷新成功后 MUST 以新凭据继续执行全部用例，并更新缓存文件
- **FR-012**: 刷新失败时，系统 MUST 发出一条警告、删除缓存文件、继续执行，且需凭据的测试跳过
- **FR-013**: 凭据有效性验证自身因网络原因无法完成时，系统 MUST 提示并跳过需凭据测试，且不得删除缓存文件
- **FR-014**: 上述所有提示 / 错误 / 警告输出中 MUST NOT 包含任何凭据字段的明文值
- **FR-015**: 登录流程失败或被用户中断时，系统 MUST 输出清晰提示、不写入缓存文件，且离线用例照常执行
- **FR-016**: 仅当显式传入 `--login` 时才允许出现登录交互；普通测试运行 MUST NOT 发起任何交互
- **FR-017**: 缓存不可用（缺失 / 损坏已删除 / 过期未刷新成功）时，既有凭据来源（`BILI_*` 环境变量、`.bilibili.cookie` 文件）MUST 照常生效，不得因本特性失效

### 关键实体

- **临时凭据缓存文件**: 存放于系统 TEMP 目录的固定名称文件；内容为 base64 编码的凭据字段集合；生命周期为"写入 → 复用 →（损坏或过期不可刷新时）删除"；同一台机器上后一次登录覆盖前一次；永不进入版本库
- **临时登录会话**: 由 `--login <type>` 触发的一次性交互登录过程（扫码或短信两种通道），产物为凭据；会话结束（成功或失败）即终结，不驻留后台
- **凭据状态**: 缓存凭据在每次测试运行时被评定的状态——有效未过期 / 已过期（可尝试刷新）/ 内容不合法 / 无法验证；状态决定该次运行走哪条取用或降级路径

## 成功标准 *(mandatory)*

### 可度量结果

- **SC-001**: 开发者从执行 `pytest --login qrcode` 到扫码确认完成登录，用户操作不超过 2 步（发起命令 + 扫码确认），登录环节耗时不超过 1 分钟
- **SC-002**: 缓存凭据有效时，第二次及以后的测试运行不含任何登录交互，需凭据用例的执行情况与手工配置凭据时完全一致
- **SC-003**: 三类异常场景（缓存缺失、内容损坏、过期且刷新失败）下，测试进程均正常结束而非崩溃，需凭据用例 100% 被标记跳过，且每个场景恰好输出一条对应级别的反馈（提示 / 错误 / 警告）
- **SC-004**: "内容损坏"与"过期且刷新失败"两场景处理完毕后，缓存文件从磁盘上消失；"缓存缺失"与"网络原因无法验证"场景不会凭空创建缓存文件
- **SC-005**: 从不使用 `--login` 且无缓存文件的既有用户视角看，凭据解析与用例跳过行为与本特性引入前完全一致（零回归）
- **SC-006**: 任意场景的全部终端输出中，凭据字段明文值出现次数为 0

## 假设

- **取用优先级**：本次 `--login` 强制登录 > TEMP 缓存文件 > `BILI_*` 环境变量 > `.bilibili.cookie` 文件。理由：临时登录是最近一次的显式意图，应覆盖环境配置；缓存不存在时按既有优先级回退，保证零回归（2026-08-31 clarify 会话确认）
- **`<type>` 合法值**定为 `phone` 与 `qrcode` 两个，别名不做约定
- **base64 仅为编码而非加密**：可接受，因缓存位于本机 TEMP、用途是临时测试，且文件不会进入版本库；若需跨用户共享机器的强保护，超出本特性范围
- **"内容正确"的判定**：文件能按"base64 → 凭据字段集合"的约定完整解码出全部必需字段；反之即"内容不对"
- **"验证有效或过期"** 指向平台核实登录态；**"刷新"** 依赖凭据中携带的配套刷新材料，材料缺失即按刷新失败路径处理
- **"抛出警告"** 指以测试框架的警告机制呈现（不中断进程），而非抛出异常终止
- 短信通道若触发极验验证码或风控二次验证，按平台既有登录能力引导用户完成，不在本特性内自建验证码服务
- 缓存文件固定名称意味着同机多账号不并存，后登录覆盖先登录（符合"临时"语义）
