# Feature Specification: NoneBot 直播适配器融合

**Feature Branch**: `nonebot`

**Created**: 2026-11-22

**Status**: Draft

**Input**: User description: "我想将 https://github.com/laowumdzz/nonebot-adapter-bilibili-live 和本项目融合在一起，在新分支 nonebot 上（目前这个分支已废弃，重新开始）"

## Clarifications

### Session 2026-11-22

- Q: 融合后适配器的导入路径怎么定？ → A: 保留 `nonebot.adapters.bilibili_live`，代码置于仓库根 `nonebot/adapters/bilibili_live/`，与 `bilibili_api` 由同一发行物安装交付。
- Q: 弹幕协议与数据层复用多少库既有实现？ → A: 部分复用——登录态用 `Credential`、账号用凭据存储管理器、HTTP 与 WebSocket 走 `BiliAPIClient` 抽象；弹幕帧解包、事件解析与事件类保留适配器自有实现（含既有 betterproto 数据类型）。
- Q: 多账号调度与连接时机是否纳入本次特性？ → A: 全部纳入（多账号按添加顺序选号、刷新失败切换、ON/AUTO/MANUAL 连接时机、存储路径覆盖）。
- Q: 开放平台（OpenBot / 身份码 / 互动玩法）这条链路是否保留？ → A: 保留但拆到后续特性；本次只融合网页弹幕（WebBot）链路，并为开放平台留出清晰扩展点。
- Q: 融合后适配器的 HTTP 与 WebSocket 连接走 NoneBot 驱动还是库内置客户端？ → A: 走 NoneBot 驱动——实现一个由驱动承载的客户端（HTTP + 四个 WebSocket 方法），适配器启动时经库注册入口装入并选中，保留用户 `DRIVER` 配置的效力。
- Q: 配置里的 cookie 字符串是否同步写进库的加密凭据存储？ → A: 不写也不接受——凭据存储是账号唯一事实源，配置只以 uid 引用存储中的账号；出现上游式 cookie 字符串即启动期报错并给出迁移指引。
- Q: 单进程预期同时监听多少直播间？ → A: 不超过 50 个；建连须并发节流，超过 50 在启动期显式报错（不静默截断）。
- Q: 「开播才连」靠什么判断开播？ → A: 逐个查询配置房间的开播状态，不要求账号关注；默认每房间 60 秒一轮、同轮相邻请求间隔不小于 2 秒，两者可配，失败只退避不加速。
- Q: 账号出问题时切换粒度是整个账号还是单个房间？ → A: 按失败类型分流——凭据类失败整号切换（该账号名下所有房间一起换），连接类失败只影响单个房间。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 网页弹幕 Bot 代码级平移接入 (Priority: P1)

已有 NoneBot 机器人作者把依赖从上游 `nonebot-adapter-bilibili-live` 换成本仓库同一个发行物后，`from nonebot.adapters.bilibili_live import ...` 的写法、事件类名、事件字段全部照旧，弹幕、礼物、上舰、进房等事件继续被插件收到；唯一需要做的一次性迁移是把账号从配置里的 cookie 字符串改为库凭据存储中的 uid 引用（启动时会明确指出该怎么改）。同时上游 0.2.6 会让主路径失效的三处缺陷被修掉（网页弹幕帧不再被丢弃、醒目留言不再报错、带粉丝勋章的网页事件不再校验失败）。

**Why this priority**: 这是「融合」的最小闭环——没有它，其余能力都无处附着；有它，融合就从「换了个仓库」变成「可以逐步下沉实现」。

**Independent Test**: 离线环境下构造适配器与 Bot，用固定的弹幕帧样本驱动分发，断言产生的事件类与关键字段；全程无外网请求、无真实凭据。

**Acceptance Scenarios**:

1. **Given** 已安装本仓库发行物与 NoneBot 运行时，**When** 按上游写法导入适配器、Bot、消息段与全部事件类，**Then** 导入全部成功且符号名与上游 0.2.6 一致。
2. **Given** 一组覆盖网页弹幕各类 cmd 的帧样本，**When** 适配器分发这些帧，**Then** 产生对应事件实例，且字段取值与上游语义一致。
3. **Given** 插件已捕获事件，**When** 调用事件既有的用户标识、会话标识等取值方法，**Then** 返回值与上游行为一致。
4. **Given** 配置仍沿用上游的 cookie 字符串写法，**When** 适配器启动，**Then** 启动失败并给出「写入凭据存储 + 以 uid 引用」的迁移提示，不静默降级、不临时接受 cookie。

### User Story 2 - 多账号凭据与自动切换 (Priority: P2)

多账号运营者把若干账号放入库的加密凭据存储，适配器按添加顺序选号建立连接；当前账号凭据失效时先尝试刷新，刷新失败自动切到下一个账号重连，机器人进程不中断。

**Why this priority**: 特性 011 已明确把「账号过期刷新 / 失败切换」划归上层调度，本次是该能力的唯一落点；没有它，多账号调度就只剩凭据存储里躺着的账号，适配器无从使用。

**Independent Test**: 以假凭据与内存态存储替身驱动调度器，构造「首个账号刷新失败」的情形，断言切到第二个账号重连，且日志与异常文本中凭据字段零命中。

**Acceptance Scenarios**:

1. **Given** 存储中有 3 个账号，**When** 适配器启动并建立连接，**Then** 使用最早添加的账号；前一个账号被移除后，下一个账号按插入顺序顶上。
2. **Given** 当前账号凭据校验失败，**When** 调度器介入，**Then** 先尝试刷新，刷新成功则原地继续，刷新失败则该账号名下所有房间一并切换到下一账号并重连。
3. **Given** 单个房间发生心跳超时或网络中断，**When** 重试流程结束，**Then** 只有该房间重连（必要时换号），其它房间的连接保持不中断。
4. **Given** 所有账号均不可用，**When** 调度器处理完毕，**Then** 以明确错误/告警收束，而不是静默空转或无限重试。
5. **Given** 任一失败路径，**When** 检查日志、异常与事件 repr，**Then** 检索不到任何凭据字段值。

### User Story 3 - 连接时机策略 (Priority: P3)

运营者按需要选择连接直播间时机：注册即连（ON）、仅在开播时连（AUTO，由轮询确定）、完全手动连（MANUAL，由业务代码显式触发）。三种策略在关闭与重载时都能干净收尾。

**Why this priority**: 长期在线的机器人在「未开播房间」上保持连接既费资源也易触发风控；这是上游没有、而决策树明确要求的能力。

**Independent Test**: 以可控时钟与假的房间状态来源驱动策略机，断言各策略在「开播 / 下播 / 启动 / 关闭」四个时点的连接动作序列。

**Acceptance Scenarios**:

1. **Given** 连接时机为 ON，**When** 适配器启动完成，**Then** 所有配置房间立即开始建立连接。
2. **Given** 连接时机为 AUTO，**When** 目标房间从未开播变为开播，**Then** 在一个轮询周期内开始连接；反之从开播变为下播，**Then** 断开该房间连接并等待下一次开播。
3. **Given** 连接时机为 MANUAL，**When** 适配器启动，**Then** 不发起任何连接，直到业务代码显式调用连接。
4. **Given** 任一策略下适配器被关闭，**When** 关闭流程结束，**Then** 所有后台任务已取消、所有连接与客户端实例已关闭，重复关闭不报错。

---

### User Story 4 - 适配器 API 调用复用库能力 (Priority: P4)

插件作者通过 Bot 的 API 调用入口使用弹幕发送、直播间信息查询、禁言/解禁等能力；这些调用与库内调用共享同一套登录态、客户端抽象与反爬参数注入，可被自定义客户端整体替换。

**Why this priority**: 这是「融合」而非「拼装」的价值所在——避免项目内出现两套 WBI/buvid 实现与两套 HTTP 栈。

**Independent Test**: 以注册的假客户端捕获请求，断言适配器的 API 调用携带库统一注入的反爬参数与登录态，且未登录时抛项目自有异常。

**Acceptance Scenarios**:

1. **Given** 已登录账号，**When** 通过 Bot 调用发弹幕、查询房间信息、禁言与解禁，**Then** 调用成功且返回结构与库对应接口一致。
2. **Given** 未登录或缺少关键凭据字段，**When** 调用需要登录的接口，**Then** 抛出项目自定义异常（而非裸异常或第三方异常）。
3. **Given** 调用方注册了自定义客户端，**When** 适配器发起 HTTP 或 WebSocket 连接，**Then** 全部经由该客户端，不出现直连第三方 HTTP 库或驱动实现的分支。
4. **Given** 用户配置了某个支持 WebSocket 的驱动，**When** 适配器启动并建立连接，**Then** 连接确实经由该驱动建立，且同进程内库的其它调用同样走该驱动。

### User Story 5 - 融合的许可与归属合规 (Priority: P5)

维护者对外发布本仓库时，融合进来的代码保留上游 MIT 版权与许可声明，仓库整体仍为 GPL-3.0-or-later，README 说明融合来源与基线版本，且融合过程不新增任何门禁豁免。

**Why this priority**: 许可证与归属是分发前提，遗漏即合规缺陷；但不能以「放宽门禁」为代价换取进度。

**Independent Test**: 在仓库内检索上游版权行、MIT 全文、来源 URL 与基线 commit 均存在；运行全量门禁无新增豁免条目。

**Acceptance Scenarios**:

1. **Given** 融合后的仓库，**When** 检查第三方声明，**Then** 可定位上游仓库 URL、基线版本与 commit、MIT 全文与版权行。
2. **Given** 融合后的仓库，**When** 运行全量门禁，**Then** 全绿通过，且 ruff 与类型检查配置中没有为适配器新增的排除/豁免。
3. **Given** 从构建产物安装，**When** 导入库与适配器，**Then** 两者均可用，且未安装 NoneBot 运行时不影响库本身的导入。

### Edge Cases

- 多个 Bot 监听同一房间、或同一账号被重复配置：需去重并给出明确告警，不产生重复连接。
- 长短房间号混用：必须以真实房间号归一后再建连与去重。
- 连接受限与风控（412 一类）：重连需退避与次数上限，不得无上限重试。
- 心跳超时：需按既定判据断开并进入重连，而不是悬挂。
- 畸形帧、未知 cmd、压缩算法差异（brotli / zlib）：应记录并跳过，不得让解码异常终止房间主循环。
- 事件处理器抛异常：不得阻塞同房间后续事件分发。
- 开播轮询失败（接口异常/风控）：需降级与退避，不得在失败时加速轮询。
- 凭据存储文件缺失、损坏或版本不匹配：显式报错并指向重新添加账号，不静默重建。
- 凭据存储被跨事件循环访问：与库现有约束一致地显式报错（不得静默串用）。
- 关闭阶段仍有未完成任务 / 连接：必须可重复安全关闭。
- 配置中出现延后的开放平台 Bot 配置：必须显式报错说明该形态尚未支持。
- 配置以 cookie 字符串给账号，或引用的 uid 不在凭据存储中：必须在启动期明确报错，分别给出迁移指引与缺失的 uid。
- 配置房间数超过并发上限（50）：启动期明确报错并指出超出的数量，不得静默截断或只连前若干个。
- 用户配置的驱动不具备 WebSocket 能力：必须在启动期明确报错并指明原因，不得在后台反复失败。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 适配器 MUST 以 `nonebot.adapters.bilibili_live` 为导入路径交付，公共符号（适配器、Bot、事件类、消息与消息段、数据模型、异常）名称与上游基线版本保持一致。
- **FR-002**: 适配器与库 MUST 由同一发行物交付，用户在同一个安装中获得两者；未安装 NoneBot 运行时 MUST NOT 影响库本身的导入与使用。
- **FR-003**: 本仓库 MUST 继续保持 GPL-3.0-or-later 分发，并 MUST 保留上游 MIT 许可全文、版权行、来源仓库 URL 与基线版本/commit。
- **FR-004**: 适配器 MUST 以库的凭据存储为账号的唯一事实源；配置 MUST 通过账号标识（uid）引用存储中的账号。配置中出现上游式 cookie 字符串时 MUST 在启动期显式报错并给出迁移指引（先写入凭据存储、再以 uid 引用），MUST NOT 静默忽略、临时接受或另立一套凭据表示。
- **FR-005**: 账号选择 MUST 遵循凭据存储的插入顺序，并能按当前顺序选号；账号的新增与移除由运维经库的凭据存储 API 完成，适配器每次启动 MUST 重新读取存储以反映最新顺序与集合，MUST NOT 自行增删账号。
- **FR-006**: 当前账号凭据失效时 MUST 先尝试刷新；刷新失败 MUST 切换到下一个可用账号；全部账号不可用 MUST 以明确错误收束。切换粒度 MUST 按失败类型区分：凭据类失败（登录态无效、刷新失败）MUST 触发该账号名下所有房间整体切号；连接类失败（网络中断、心跳超时、风控响应）MUST 只在该房间内重试并按需换号，MUST NOT 连带断开其它房间。
- **FR-007**: 连接时机 MUST 支持「注册即连 / 开播才连 / 手动连」三种取值且可配置，默认值 MUST 与上游行为兼容（启动即连）。
- **FR-008**: 「开播才连」策略 MUST 逐个查询配置房间的开播状态来决定连接与断开，MUST NOT 依赖「账号已关注这些房间」这类隐性前提；默认每房间 60 秒一轮，同一轮内相邻请求间隔 MUST 不小于 2 秒（房间多时整轮自然拉长），两个数值均 MUST 可配置；查询失败 MUST 退避，MUST NOT 在失败时缩短间隔。
- **FR-009**: 单房间隔离：每个房间的连接、重连与心跳 MUST 相互独立，单个房间失败 MUST NOT 影响其他房间。
- **FR-010**: 接收链路 MUST 覆盖上游网页弹幕链路的全部可实例化事件（上游 41 个可实例化事件中，除 2 个开放平台专属事件外，其余 39 个均在本次范围），且字段语义与上游一致。
- **FR-010a**: 上游 0.2.6 的三处已确认缺陷 MUST NOT 被复现：网页 `DANMU_MSG` 主路径帧（无顶层 `data` 键）MUST 正常产生弹幕事件；醒目留言（含中/日文变体）MUST 正常产生事件；携带粉丝勋章的网页事件 MUST 通过校验并保留勋章字段（含点亮状态）。融合后的行为以修正后语义为兼容基线。
- **FR-011**: 所有 HTTP 调用 MUST 经由库的客户端抽象层发起，MUST 支持经库的注册入口替换实现。适配器启动时 MUST 装入并选中一个由 NoneBot 驱动承载的客户端实现，使用户配置的驱动继续生效；除该客户端实现内部之外，MUST NOT 在任何业务代码中直接使用 NoneBot 驱动或具体 HTTP 库。
- **FR-012**: 所有 WebSocket 连接 MUST 经由库的客户端抽象层的 WebSocket 能力发起；驱动承载的客户端实现 MUST 覆盖 HTTP 与 WebSocket 两类能力，MUST 在驱动不具备 WebSocket 能力时于启动期给出明确错误。
- **FR-013**: 反爬要素（WBI 签名、buvid、bili_ticket）MUST 复用库内集中实现，适配器 MUST NOT 自带一份签名或指纹获取实现。
- **FR-014**: 事件分发 MUST 与 NoneBot 的事件处理流程对接；单个处理器抛出异常 MUST NOT 中断该房间的后续分发，同一房间内的事件 MUST 保持帧到达顺序。
- **FR-015**: 凭据字段值 MUST NOT 出现在任何日志、异常文本、事件 repr 或错误提示中。
- **FR-016**: 配置 MUST 支持凭据存储路径的显式覆盖（供以本地存储插件管理路径的场景），未配置时 MUST 使用库默认路径。
- **FR-017**: 关闭流程 MUST 取消所有后台任务、关闭所有连接与客户端实例，且 MUST 可重复安全调用。
- **FR-018**: 本次延后的开放平台 Bot 形态 MUST 在配置出现时显式报错说明不支持，MUST NOT 静默忽略或提供半可用连接。
- **FR-019**: 适配器的公共能力 MUST 具备完整类型注解与中文 docstring，并通过与库同口径的 lint、类型与文档门禁，MUST NOT 新增排除或豁免。
- **FR-020**: 测试 MUST 遵守库的分层口径：解析、分发、调度、配置校验等纯本地逻辑以离线用例覆盖；真实连接类验收属集成层，仅读语义，缺凭据时自动跳过。
- **FR-021**: 连接生命周期 MUST 包含心跳保活与断线自动重连；重连 MUST 有退避与次数上限，主动关闭后 MUST NOT 触发重连。
- **FR-022**: 配置 MUST 以显式字段表达分支语义（MUST NOT 依赖字段集合的隐式推断来决定配置分支或账号形态，避免误写被静默解释为另一种形态）；配置缺失或类型不合法时 MUST 在启动期显式报错并指明缺失/非法项，MUST NOT 启动后静默按默认值降级。
- **FR-023**: 单进程并发规模 MUST 支持同时监听 50 个直播间；建连 MUST 受并发节流（分批或信号量），MUST NOT 在启动瞬间无节制并发建连；配置房间数超过 50 时 MUST 在启动期显式报错，MUST NOT 静默截断或丢弃。

### Key Entities

- **适配器与 Bot**：NoneBot 适配器实体与其承载的直播 Bot；本次仅网页弹幕 Bot，开放平台 Bot 延后。
- **账号凭据**：由库登录态对象表示，连同其插入顺序构成多账号序列；落盘由库的加密凭据存储承担。
- **房间订阅**：一条「房间 + 账号 + 连接」的运行单元，含真实房间号、连接状态、重连计数与心跳状态。
- **连接时机策略**：注册即连 / 开播才连 / 手动连，决定房间订阅的启动与停止时点。
- **事件族**：消息、通知、元事件三类事件及其可实例化子类型，承载弹幕、礼物、上舰、榜单、房管等业务语义。
- **消息与消息段**：适配器对外暴露的消息表达，供插件构造与解析。
- **第三方许可声明**：上游项目来源、版本、commit、版权行与 MIT 全文。

## Assumptions

- 上游基线取 `nonebot-adapter-bilibili-live` 0.2.6（commit `3f2c9bc2e74e02eaeb1a2192335f84eb3391782e`），以该版本的事件字段与配置形态作为兼容基线。
- 适配器代码位于仓库根 `nonebot/adapters/bilibili_live/`；因仓库根布局，开发环境下该目录与已安装的 NoneBot 包同名，需在开发流程中约定可验证的导入方式（由后续计划阶段裁决具体做法）。
- 门禁检查范围扩大到适配器目录（`ruff` 与类型检查的 include 扩展），而不是把该目录排除在检查之外。
- NoneBot 运行时作为可选依赖引入；只有导入适配器时才需要它。版本下限为 2.5.0（更早版本的 aiohttp 驱动在 WebSocket 正常关闭时会漏出 `TypeError`），且弹幕链路只在实现 WebSocket 能力的驱动下可用——纯 HTTP 驱动（如 nonebot 的 httpx 驱动）只能跑 REST，启动期必须明确报错。
- 驱动承载的客户端经库的进程级选中生效。由于库在导入时已默认选中内置客户端（无法区分「默认」与「用户显式选择」），适配器启动时 MUST 接管选择并以日志记录；用户可在适配器启动后再次经注册入口覆盖，以保持"自定义客户端可整体替换"。
- 融合后不单独维护适配器版本号，也不单独发布到包索引（宪章禁止上传 PyPI），版本随库单一版本源推进；下游经 git 或 Release 产物安装。
- 适配器内部仍以既有 betterproto 数据类型承载事件字段（本次不做数据层替换），但网络与凭据层全部下沉到库。
- 以单进程、单事件循环运行为主；凭据存储的跨循环限制按库既有约束显式暴露。
- 账号配置形态的变更是破坏性变更：上游的 cookie 字符串写法不再被接受，提交信息 MUST 标注 `BREAKING CHANGE`，README 与迁移说明 MUST 给出「先写入凭据存储、再以 uid 引用」的完整步骤。
- 规模目标为单进程同时监听 50 个直播间；更高规模不在本次验收范围，超过即显式拒绝（见 FR-023）。
- 开播检测默认参数为「每房间 60 秒一轮、同轮相邻请求间隔 ≥ 2 秒」，均可配置；默认值以不触发风控为先，而非以最快响应为先。
- 失败分类的完整清单（哪些 HTTP 状态码、业务码与异常归入凭据类，哪些归入连接类）由 plan 阶段细化；但分类本身 MUST 显式、可测试，MUST NOT 用「一律重连」的兜底掩盖。
- 上游项目自身没有测试基线，本次回归基线由「固定帧样本 + 事件字段快照」自建。
- 上游 0.2.6 的网页链路存在三处已运行时确认的缺陷（网页 `DANMU_MSG` 因「缺少顶层 data」守卫被静默丢弃、醒目留言因 `rmb` 取值方式必抛 `KeyError`、网页事件勋章字段校验因 `is_lighted` / `is_light` 命名不一致而失败）。本次以「修正后的正确行为」为兼容基线，不以复现缺陷作为兼容目标；这三处修复属本特性的验收内容（FR-010a / SC-010）。
- 开放平台链路（身份码、开放平台 WebSocket、互动玩法专属事件）不在本次范围，但配置结构、客户端边界与事件注册表需预留扩展点，避免后续特性返工；上游的 2 个开放平台专属事件类为保持导入兼容而保留定义，本次不会由任何链路产生。
- 账号「刷新」指库既有的 cookie 刷新流程；刷新所需字段缺失时直接视为刷新失败并切换。
